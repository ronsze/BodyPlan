# implement

목적: 코드 변경 요청을 수준에 맞는 단계 조합으로 수행한다.

## 단계

① 요청 접수 → ② 계획 → ③ 작업 환경 → ④ 구현 → ⑤ 리뷰 → ⑥ 테스트 → ⑦ 기록

모든 작업이 모든 단계를 거치지 않는다. ①~②에서 수준을 판정해 단계를 취사선택한다.

## 수준 판정

판정 축은 **새 계약이 생기는가**다. 계약 = State 필드 / Intent / Effect / NavKey / Repository·DAO 시그니처 / 호출부가 여럿인 공용 코드의 public 시그니처.

| 수준 | 기준 | 적용 단계 |
|---|---|---|
| 탐색 | 산출물이 코드가 아니라 답인 요청 — "되나?", "가능한가?", "대충 확인만". 코드를 써도 버린다 | ④ — 결과는 답·추천으로 보고, 코드는 커밋하지 않고 폐기를 명시 |
| 경미 | 결과가 지시에 이미 특정된 지점 변경 — 문구·값·경로·단순 스타일 | ④ |
| 경계 내 | 로직 변경이 있으나 계약이 추가·변경되지 않음. 호출부가 하나뿐인 신규 헬퍼는 계약으로 보지 않는다 | ②(채팅) ④ + 컴파일·셀프 리뷰 |
| 표준 | 계약 중 하나라도 추가·변경됨, 또는 호출부가 여럿인 공용 코드를 고침 | ②(채팅) ④ ⑤ ⑥ |
| 복합 | 새 구조가 생김 — 신규 화면·기능, 여러 계층에 걸친 영향 | 전 단계 |

판정이 갈리면 상위 수준을 택한다. **판정 결과는 착수 전에 "수준: 경계 내 — 근거 한 줄" 형태로 첫 줄에 말한다** — 사용자가 뒤집을 지점이다. 탐색 결과를 남기자는 요청은 새 요청이므로 다시 판정한다. ⑦ 기록은 수준과 무관하게 요청된 경우에 수행한다.


**독립적으로 계약을 갖는 단위가 둘 이상이면 먼저 분할을 합의한다.** 요청이 서로 독립적인 기능·화면 묶음을 여럿 담고 있으면 세부를 파고들기 전에 그 사실을 먼저 말하고, 단위와 구축 순서를 합의한 뒤 단위별로 다시 판정한다. 하나의 계획에 전부 담으려 하지 않는다.

**재판정은 어느 단계에서든 일어난다.** 판정 시점에 없던 계약 변경이 드러나면(경계 내인데 State 필드가 필요해짐, 표준인데 새 화면이 필요해짐 등) 그 자리에서 멈추고 상향 재판정해 여기로 돌아온다. 올라간 수준의 적용 단계를 ②부터 다시 밟고 사용자와 합의한다. "거의 다 했으니 마저 한다"로 수준을 유지하지 않는다. 판정은 올라가기만 하고 내려가지 않는다.

## 추측 금지

주어진 컨텍스트로 정확한 판단이 불가능하면 추측으로 메우지 않고 사용자에게 묻는다. 모든 단계에 적용된다.

- 판정 기준: 해석이 둘 이상 가능하고 해석에 따라 산출물이 달라지면 묻는다. 해석이 갈려도 산출물이 같으면 묻지 않고 진행한다.
- 리포에서 확인 가능한 사실은 묻기 전에 먼저 확인한다. 확인해서 얻을 수 없는 것만 묻는다.
- 질문은 모아서 한 번에 하고, 답에 의존하지 않는 부분은 먼저 진행한다. 답을 받기 전에 그 부분을 구현하지 않는다.

## 단계 정의

1. **요청 접수**: 요구 내용을 확정한다. 완료 후 후속 작업(커밋 등)은 첫 요청에 명시됐거나 완료 시점에 요청된 것만 수행한다.
2. **계획**: 수준에 따라 형태가 다르다. 어느 수준이든 합의 후 착수하며, 이 계획이 이후 단계의 근거다 — 후속 단계의 수정은 계획과 대조해 수행한다.
   **합의되지 않으면 어디로 돌아갈지는 반려 사유가 정한다.** 접근 자체가 반려되면 방향 합의부터 다시 하고(복합은 계획 파일을 새로 쓴다), 접근은 유지한 채 내용이 반려되면 계획만 고쳐 다시 제시한다. 반려된 접근은 계획 파일의 `버린 안`에 이유와 함께 적는다. 합의 없이 ③으로 넘어가지 않는다.
   - **경계 내**: 채팅에 접근·수정 파일·검증 방법을 3~5문장으로 제시한다. 파일을 만들지 않는다.
   - **표준**: 채팅에 수용 조건 / 파일별 작업 / 회귀 대상 3개 절을 제시한다. 파일을 만들지 않는다.
   - **복합**: 먼저 채팅에서 방향을 합의한다 — 사용자가 접근을 고른 뒤에 계획 파일을 쓴다. 방향 합의 전에 계획 파일을 쓰기 시작하지 않는다. 합의된 방향으로 요구 정리, 영향 범위·수정 파일, 검증 방법, 적용할 단계를 제시한다. 영향 범위 조사는 Explore 에이전트에 위임한다. `references/plan.md`를 읽고 그 구조로 계획을 `plans/<topic>-design.md` 파일로 남긴다. 쓴 계획은 `references/plan.md`의 `자기 대조`를 수행해 지적을 고친 뒤, 자기 대조 결과와 함께 사용자에게 제시해 리뷰를 받고, 발견을 반영해 합의한다. 계획 리뷰는 사용자가 하며 서브에이전트에 위임하지 않는다.
3. **작업 환경**: 지시에 따라 새 브랜치+worktree 또는 현재 브랜치에서 작업한다. 지시가 없으면 탐색·경미·경계 내는 현재 브랜치에서 작업하고, 표준 이상만 묻는다. 단 현재 브랜치가 기본 브랜치(`master`)면 수준과 무관하게 묻는다 — 코드 변경을 기본 브랜치에 바로 쌓지 않는다.
4. **구현**: 착수 전에 계획을 다시 읽고 지금도 유효한지 대조한다 — 지목한 파일·심볼이 실재하는지, 합의 이후 코드가 바뀌지 않았는지. 우려가 있으면 구현을 시작하기 전에 제기한다. 그 뒤 계획 기반으로 수행한다. 계획 없는 수준(탐색·경미)이면 주변 코드의 표기를 따라 지시 그대로 수행한다. 탐색은 답을 얻는 최소 비용으로만 만들고 결과 보고에 폐기 대상임을 적는다.
   - **경계 내 검증**: `./gradlew :app:compileDebugKotlin`을 실행해 통과를 확인하고(`:core:*`는 전부 `:app` 의존 그래프에 있어 함께 컴파일된다), diff를 code-reviewer의 로직·재사용 기준으로 직접 훑는다. 서브에이전트에 위임하지 않는다.
5. **리뷰**(표준 이상): code-reviewer에 위임한다 — 변경 성격에 맞는 기준을 지정. 발견은 계획과 대조해 처리한다: 상은 수정하고, 중은 수정안을 사용자에게 제시해 합의하고, 하는 보고만 한다. 계획과 어긋나는 방향이면 계획을 갱신하고 사용자에게 알린다.
6. **테스트**(표준 이상): ViewModel·domain·data 계층 변경이 있으면 test-engineer에 위임한다 — 영향 범위는 클래스 목록으로 지정하고, ②에서 합의한 수용 조건(복합 수준은 계획 파일의 `수용 조건` 절 그대로)을 함께 넘긴다. 보고의 수용 조건별 커버 여부를 계획과 대조해, 덮지 못한 조건이 있으면 사용자에게 알린다. Compose UI만 바뀌었으면 위임하지 않고 컴파일 + Preview 렌더 확인으로 대체한다. 최종 게이트다.
   ⑤와 ⑥이 둘 다 필요하면 한 메시지에서 동시에 위임한다. ⑥의 실패 수정이 생기면 그 변경분만 재리뷰한다.
7. **기록**: 커밋, 작업 보고서 작성. 소요 시간은 사용자가 시작·종료 시각을 준 경우에만 적는다 — 모델은 요청 시각을 관측할 수 없으므로 추정하지 않는다. 토큰 사용량도 추정하지 않는다.

## 경계

- 대상: 이 리포의 코드 변경과 그 검증·기록.
- 비대상: 통합 병합·배포, 코드를 바꾸지 않는 점검·문서 작업, 하네스 수정.

## 종료 조건

판정된 수준의 적용 단계를 모두 마치고 결과를 보고하면 완료.

## 실패 시

계획과 실제가 어긋나 진행이 불가능하면(참조 부재, 전제 불일치) 우회하지 않고 멈추고 사용자에게 묻는다.

## 검증

- 호출 적절성: "버튼 문구 바꿔줘"(대상)와 "이 코드 설명해줘"(비대상)가 description만으로 판별되는지 확인한다.
- 수준 판정: 대표 요청 다섯 개("Room으로 이 조회 되나?" / 문구 수정 / 기존 화면의 스크롤 동작 추가 / State 필드 추가 / 신규 화면)로 판정이 표와 일치하고, 판정이 착수 전 첫 줄에 말해지는지 확인한다.
- 추측 금지: 값·대상이 특정되지 않은 요청("여백 좀 늘려줘")에서 임의 값으로 진행하지 않고 묻는지, 리포에서 확인 가능한 사실은 묻지 않고 확인하는지 확인한다.
- 상향 재판정: 경계 내로 시작한 작업에 State 필드를 요구하는 조건을 끼워 넣어 구현 중 멈추고 재판정한 뒤 ②부터 다시 밟는지 확인한다.
- 미승인 경로: 제시한 계획을 접근 단위로 한 번, 내용 단위로 한 번 반려해 각각 방향 합의·계획 수정으로 돌아가는지 확인한다.
- 요청 분해: 독립 기능 둘을 한 요청에 담아 세부 질문 전에 분할을 먼저 제안하는지 확인한다.
- 기본 브랜치: `master`에서 경미 수준 요청을 넣어 브랜치를 묻는지 확인한다.
- 목적 달성: 표준 이상 작업 하나를 실제 수행해 계획→구현→리뷰→테스트 흐름이 계획을 근거로 이어지는지 확인한다.
- 비용: 경계 내 작업 하나를 실제 수행해 서브에이전트 위임 없이 끝나는지 확인한다.
