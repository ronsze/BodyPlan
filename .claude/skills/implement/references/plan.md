# 계획 파일 작성법

목적: 복합 수준 작업의 계획을 이 문서만 읽고 구현에 착수할 수 있는 계획 파일로 남긴다. 경계 내·표준 수준은 계획 파일을 만들지 않는다 — `SKILL.md`의 ② 계획 참조.

`plans/<topic>-design.md`에 쓴다. `<topic>`은 작업 대상을 나타내는 소문자 케밥 케이스다(예: `workout-log-design.md`). 작업 완료 후에도 삭제하지 않고 코드와 함께 커밋한다.

## 작성 선

**계약까지 쓰고 구현체는 쓰지 않는다.** State 필드 목록은 쓰되 reduce 로직은 쓰지 않는다. 응답 스펙은 사용 필드와 매핑만 쓰고 전문을 옮기지 않는다. 계획이 길어지면 구현 단계가 읽지 않는다.

화면 구성의 재사용 판정은 시그니처(파라미터명·타입·기본값)까지만 옮긴다. 리터럴 인자를 채운 실제 호출 코드나 컴포저블 트리 전체를 그대로 옮겨 적지 않는다 — 그건 구현 단계의 몫이다.

각 절은 지우지 않는다. 해당 없으면 `해당 없음`이라고 적는다 — 빈칸은 누락과 구분되지 않는다.

**열어 본 것만 적는다.** 파일 경로·심볼·재사용 판정은 그 파일을 열어 확인한 뒤에 적는다. 조사 에이전트의 "재사용 가능"·"그대로 쓸 수 있다"는 요약이지 계약이 아니다 — 계약으로 올리려면 대상의 필수 파라미터·필드를 계획에 옮겨 적어야 하고, 옮겨 적을 수 없으면 `미확인`으로 적는다. 심볼 이름에서 파일명을 추론하지 않는다.

**도메인 타입은 리포에서 먼저 찾는다.** 표준 라이브러리 타입(`DayOfWeek`, `LocalTime` 등)을 쓰기 전에 `core/domain/model`에 대응 타입이 있는지 확인하고, 있으면 그것을 쓴다.

## 절 정의

문서는 **설계**와 **실행** 두 그룹으로 나눈다. 설계는 사용자 승인 대상이고, 실행은 승인된 설계에서 도출되는 것이다. 반려도 이 경계를 따른다 — 접근이 반려되면 설계부터, 내용이 반려되면 실행만 고친다.

### 설계 절

| 절 | 내용 | 판정 기준 |
|---|---|---|
| 작성일 | 계획을 쓴 날짜 `YYYY-MM-DD` | 제목 바로 아래에 둔다. 커밋 후 남는 문서이므로 언제 시점의 판단인지 드러나야 한다 |
| 요약 | 무엇을 만드는지 3줄 | 재개 시 첫 진입점 |
| 배경 | 이 요구가 나온 맥락 | 구현 중 분기 판단에 쓰이는 것만. 요청에 없으면 생략 |
| 수용 조건 | 완료를 판정하는 검증 가능한 문장 목록 | 테스트 단계에 그대로 넘어가는 근거다. 성공 시나리오만 적지 않고, 대상에 해당하는 실패 경로(조회 실패·빈 결과·저장 실패)를 조건으로 함께 적는다 |
| 비목표 | 이번에 하지 않는 것 | 스코프 확장을 막는다. **이번 변경에 필요하지 않은** 인접 파일 정리·리팩터링은 여기 적어 배제한다. 반대로 손대는 코드 자체의 결함이 작업을 막으면 배제하지 말고 파일별 작업에 포함한다 |
| 데이터 계약 | 데이터 소스(DAO 쿼리·엔티티), 필드별 Entity→Domain 매핑과 **귀착지** | 입출력 필드를 하나도 빼지 않고 적고, 각 필드가 어느 상태 필드·화면 요소로 가는지 적는다. 쓰지 않는 필드는 `미사용`이라고 적는다 — 빠뜨린 것과 구분된다 |
| 상태 계약 | State 필드 / Intent / Effect 목록 | 화면별로 나눠 적는다. 호출이 실패했을 때 어떤 State·Effect가 되는지 함께 적는다 — 재시도 여부와 에러 전파 경로를 포함한다 |
| 화면 구성 | 컴포넌트 트리, 요소별 재사용·확장·신규 판정, **화면별 상태**, 시안 노드 id, 카피 원문 | 재사용 판정은 대상 심볼을 열어 확인한 뒤 적는다. 화면마다 로딩·빈·에러·권한 상태에서 무엇을 보여줄지 적는다. Figma 시안이 있으면 화면·구성요소마다 대응하는 노드 id를 적는다. 화면에 나오는 문구는 원문 그대로 옮긴다 |
| 네비게이션 | NavKey, 인자, 진입·복귀 경로 | |
| 버린 안 | 검토했으나 채택하지 않은 안과 그 이유 — 계획 파일 전 채팅 방향 합의에서 버린 접근을 포함한다 | 재개·리뷰 시 같은 안이 다시 올라오는 것을 막는다 |

### 실행 절

| 절 | 내용 | 판정 기준 |
|---|---|---|
| 파일별 작업 | 경로 / 신규·수정 / 할 일 한 줄 | 모듈·계층 경계를 넘는 파일이 빠지지 않았는지 확인한다 |
| 구현 순서 | 착수 단위, 단위별 **쓰는 것·만드는 것**, 검증·커밋 경계 | 단위는 독립적으로 검증 가능한 최소 크기다. 단위마다 앞 단위에서 받아 쓰는 심볼과 뒤 단위가 쓸 심볼을 적는다 — 이것이 순서의 근거이며, 어느 단위에서도 만들어지지 않는 것을 쓰면 계약이 빠진 것이다. 단위마다 실행할 검증 명령(`:app:compileDebugKotlin`, `:app:testDebugUnitTest` 등)과 어디서 커밋할지를 적는다 |
| 회귀 대상 | 공용 파일을 고칠 때 함께 확인할 기존 호출부 | 공용 컴포넌트·모델·네비게이션 규약을 건드리면 반드시 적는다 |

## 자기 대조

계획을 쓴 직후, 사용자에게 제시하기 전에 작성자가 수행한다. 계획에 대한 유일한 사전 검증이므로 생략하지 않는다.

**구현 단계에서 실제로 문제를 일으킬 것만 지적으로 본다.** 계약이 빠졌거나, 서로 모순되거나, 해석이 갈려 다른 것을 만들게 될 문장 — 이것이 지적이다. 문구 다듬기, 절마다 상세도가 다른 것, 취향 차이는 지적이 아니다. 이런 항목은 고치지도 보고하지도 않는다.

지적은 제시 전에 고친다. 고칠 수 없는 것(사용자 답이 필요한 것)만 제시에 함께 낸다.

- 수용 조건마다 그것을 일으키는 Intent와 결과를 내는 Effect가 상태 계약에 있는가.
- 수용 조건에 실패 경로 조건이 있는가 — 대상에 해당 없는 축은 그 사실을 적었는가.
- 화면 구성에 `재사용`으로 적은 심볼마다 그 파일을 열어 시그니처를 확인하고 인자 이름을 그대로 옮겼는가. modifier 체인 순서와 하드코딩된 치수까지 봤는가.
- 상태 계약의 각 필드가 데이터 계약이나 화면 구성에서 나오는가. 어디서도 안 나오는 필드가 있는가.
- 상태 계약의 각 필드에 초기값이 적혀 있는가. 재사용하는 Intent·Effect·함수의 기본값 없는 인자를 무엇으로 채우는지 적었는가.
- "착수 시 확인"으로 남긴 것이 지금 grep 한 번으로 정해지지 않는가.
- 데이터 계약의 각 필드에 귀착지 또는 `미사용`이 적혀 있는가.
- 파일별 작업이 위 계약을 전부 덮는가. 계약에 있는데 손댈 파일이 없는 항목이 있는가.
- 구현 순서의 각 단위가 `쓰는 것`으로 적은 심볼이 앞 단위의 `만드는 것`이나 기존 코드에 있는가 — 어디서도 만들어지지 않는 것을 쓰는 단위가 있는가.
- 뭉뚱그린 표현이 남았는가 — `TBD`·`TODO`·"적절히 처리"·"에러 처리 추가"·"위 내용에 대한 테스트 작성"은 계획이 아니라 미룸이다. 실제 내용으로 바꾸거나 지금 정할 수 없는 이유를 적는다.
- 같은 것을 가리키는 이름이 절마다 같은가 — 계약 절의 심볼·필드명과 파일별 작업·구현 순서에 적은 이름이 철자까지 일치하는가.
- 요약·배경이 비목표·확정 전제와 어긋나지 않는가.
- 사용자가 답을 준 결정이 그 사실과 함께 적혀 있는가 — 문서만 읽는 사람에게 작성자의 임의 판단으로 보이면 안 된다.
- 화면마다 로딩·빈·에러·권한 4개를 전부 적었는가 — 하나라도 비었으면 `해당 없음`을 채워 넣었는가.
- 화면 구성의 재사용 판정이 시그니처를 넘어 리터럴 인자·전체 컴포저블 트리 코드로 넘어간 곳이 있는가 — 있으면 시그니처 수준으로 되돌렸는가.

### 결과 보고

자기 대조를 마치면 결과를 계획 파일 말미에 적는다.

```
자기 대조: 통과 | 미해결 있음 (대조 N/N)
- 고침: [절 이름], [절 이름]
- 미해결 [절 이름]: 무엇이 비었는지 — 구현 단계에 어떤 문제가 되는지 / 사용자에게 무엇이 필요한지
```

`N/N`은 대조한 항목 수와 위 목록의 전체 항목 수다 — 분모에 못 미치면 대조를 마치지 않은 것이다. 고친 항목은 절 이름만 적고 내용은 적지 않는다. 계획을 제시할 때 응답에는 미해결 항목만 옮긴다 — 미해결이 없으면 자기 대조를 응답에 내지 않는다.

## 검증

- 자기 대조 수행: 계획 파일의 `N/N` 분모가 체크리스트 항목 수와 일치하는지 확인한다.
- 자족성: 이 계획 파일과 요청 원문만으로 구현 착수가 가능한지 — 포인터만 있고 내용이 없는 절이 남았는지 확인한다.
- 미룸: "구현 시 확인·구현 시 결정"으로 남긴 항목이 지금 결정할 수 없는 것인지 확인한다. 문서를 읽거나 코드를 보면 정해지는 것을 미뤘으면 계획 단계에서 정한다.
- 자기 정합: 요약·배경이 비목표·확정 전제와 어긋나지 않는지 확인한다. 범위에서 뺀 것은 비목표에만 적지 말고 요약·배경에서도 드러나야 한다.
- 실재성: 계획이 지목한 파일·컴포넌트·심볼이 리포에 실제로 존재하는지 확인한다.
